# Validation

## Evidence Ceiling

This specification gate can reach only evidence rung 1: static/schema evidence
over five new Markdown files. It does not implement or validate the future
governance behavior and does not prove independent review, Git integration,
CompactHandoff runtime behavior, provider, deployment, pilot, production,
human acceptance, or measured efficiency improvement.

A future delivery may reach at most rung 2 after focused deterministic tests,
physical CLI validation, and local v3 contract checks pass. Later rungs require
separate evidence and authority.

## Specification-Gate Allowlist

Exactly these paths may be new or modified in this gate:

```text
specs/2026-08-30-governance-cadence-and-handoff-v3/spec.md
specs/2026-08-30-governance-cadence-and-handoff-v3/requirements.md
specs/2026-08-30-governance-cadence-and-handoff-v3/plan.md
specs/2026-08-30-governance-cadence-and-handoff-v3/tasks.md
specs/2026-08-30-governance-cadence-and-handoff-v3/validation.md
```

No staged path, generated file, ignored/cache artifact, environment change,
Git mutation, network, provider, Graphify, plugin mutation, or cleanup is
permitted.

## Specification-Gate Checks

Run from repository root without staging:

```bash
git rev-parse --show-toplevel
git rev-parse HEAD
git rev-parse HEAD^{tree}
git diff --cached --quiet
git status --porcelain=v1 --untracked-files=all
find specs/2026-08-30-governance-cadence-and-handoff-v3 -type f -print
git diff --check -- specs/2026-08-30-governance-cadence-and-handoff-v3
```

Because ordinary `git diff --check` does not inspect wholly untracked files,
also run a read-only direct check that every file is valid UTF-8, non-empty,
ends in exactly one final newline, and contains no trailing whitespace. Do not
stage or use intent-to-add to increase check coverage.

## Structural Assertions

1. Inventory equals the five-path allowlist exactly.
2. `spec.md` contains status/authority, problem, outcome, users, canonical
   terms, precedence, settled decisions, gate budgets, grouped decisions,
   dispatch, retry/harness, v3 selection/trust/version, interfaces, scope,
   human review, security/data boundaries, migration, non-goals, and stops.
3. `requirements.md` contains unique `YCH-*` identifiers and every family is
   represented in the acceptance matrix.
4. `plan.md` contains objective, affected files, assumptions, risks, delivery
   phases, verification, definition of done, and unresolved decisions.
5. `tasks.md` distinguishes owner decisions, delivery, TDD, v3 transfer,
   independent review, correction/re-review, close/Git, and external rungs.
6. The complete future review candidate is exactly five immutable spec paths
   plus eight delivery mutation paths.
7. Every file preserves rung-1 wording and denies successor authority.

## Contradiction Negatives

The package fails if it positively states or implies any of these:

- owner approval gates and executor tasks are the same count or identity;
- a normal gate budget suppresses a real contingency, promotion, human
  decision, external rung, or repository-required task;
- Level 0 normally requires a new spec or mandatory CompactHandoff v3;
- Level 1/2 with accepted spec normally requires a fourth owner decision
  without a classified contingency;
- Level 1/2 without a spec may implement before the spec candidate is accepted;
- task creation, handoff issue/verify, PASS, review, receipt, acceptance, commit,
  or push auto-authorizes a successor;
- grouped decisions merge grants, task identities, consumption, preconditions,
  or receipts;
- more than one dormant mechanical retry or a third invocation is allowed;
- generic retry or harness-repair wording is exact authority;
- harness repair auto-resumes candidate work or counts as semantic RED;
- CompactHandoff authenticates authority, proves manifest/Git truth, consumes a
  grant, prevents replay, accepts bytes, or replaces independent preflight or
  Receipt Capsule v1;
- required v3 issue/verify failure silently falls back to v2, plain text,
  regenerated bytes, or alternate transport;
- plugin code, schemas, fixtures, skills, references, or cache paths are copied
  or wrapped into the repository;
- a second administrative closeout or post-Git reconciliation is mandatory
  without semantic change;
- the audit or gate budget is presented as measured efficiency evidence; or
- the spec author accepts its own package or authorizes delivery/Git/external
  action.

Negative assessment must distinguish allowed conditional language and explicit
prohibitions from positive authority. Keyword presence alone is not proof.

## Future Delivery Positive Checks

The delivery validation contract must include:

1. focused public-seam tests for `validate(repo)`;
2. physical CLI PASS/FAIL tests with stable diagnostics;
3. exact gate-budget and canonical-term assertions;
4. negative fixtures for task/gate conflation, wrong gate counts, hidden
   contingencies, measured-efficiency claims, excess retries, generic retry or
   repair, automatic harness resume, v3 authority/truth overclaim, missing v3
   selection, silent fallback, obsolete minimum version, and recursive
   closeout;
5. adapter assertions preserving policy `1.4`, profile `provider-eval`, and
   minimum `0.11.0`;
6. pointer checks proving local docs do not copy plugin implementation or
   universal contract text;
7. exact complete candidate inventory across changed, staged, and untracked
   paths;
8. `git diff --check` plus direct checks for any untracked file;
9. no-cache/no-generated-artifact assertions after tests and validators;
10. a required delivery-to-review CompactHandoff v3 issue/verify exercise with
    an independently observed candidate manifest; and
11. independent `FULL` review of Standards -> Spec -> Evidence -> Operations.

Representative commands must be finalized against the accepted delivery fixed

No `make test-release`, broader product suite, network, provider, Graphify,
deployment, pilot, production, plugin installation, or publication command is
implied. A future owner may authorize additional proportional checks separately.

## Acceptance Criteria

- **AC-001:** The five-file spec inventory and fixed point are exact.
- **AC-002:** Every `YCH-*` requirement maps to a task and validation proof.
- **AC-003:** Normal gate budgets are unambiguous and separate from task count.
- **AC-004:** Grouped decisions preserve distinct grants and fail-closed
  intermediate preconditions.
- **AC-005:** Retry and harness behavior matches the universal authority
  contract without copying it.
- **AC-006:** V3 selection is risk-based, new issuance is v3, required-boundary
  failures stop without fallback, and transport creates no authority.
- **AC-007:** Future delivery scope is exact and excludes plugin/product/external
  mutation.
- **AC-008:** Evidence is capped at rung 1 for this gate and no efficiency claim
  is manufactured.

## Acceptance Stops

Any fixed-point mismatch, extra path, staged delta, invalid UTF-8, trailing
whitespace, missing final newline, duplicate/missing requirement, unresolved
contradiction, copied universal contract, incomplete validation, sensitive-data
risk, or evidence overclaim stops this gate. PASS returns the five-file
candidate for owner decision and does not accept it or authorize delivery,
review, correction, Git, provider, deployment, pilot, production, or another
gate.
